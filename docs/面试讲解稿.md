# 项目3：门店评论分析与自动回复 Agent 面试讲解稿

## 一、30 秒版本

这个项目是一个门店评论分析与自动回复 Agent，面向咖啡店、餐饮门店这类本地生活场景。

项目最初是用 Python 和 Pandas 读取门店评论 CSV，完成评分统计、差评筛选、问题分类和问题分布统计。后面我把它升级成了 FastAPI 接口服务，并部署到 Render 公网环境。最后在 Dify 工作流中，通过 HTTP 请求节点调用这个 API，再让 LLM 节点自动生成门店经营分析周报和典型差评回复建议。

这个项目让我完整理解了从本地 Python 脚本，到 API 服务，再到 AI 工作流调用的落地流程。

## 二、1 分钟版本

这个项目叫门店评论分析与自动回复 Agent，主要解决门店评论人工整理效率低、差评原因不清晰、商家回复模板化的问题。

项目分成四层：

第一层是 Python 数据处理。我用 Pandas 读取门店评论 CSV，统计评论总数、平均评分、好评 / 中评 / 差评数量和占比，并筛选评分小于等于 2 分的差评。

第二层是问题分类。我通过关键词规则把评论分成等待时间、配送物流、服务态度、环境卫生、产品质量等类型，并统计各类问题的数量和占比。

第三层是 API 工程化。我把原来的分析逻辑拆到 `review_service.py`，再用 FastAPI 在 `main.py` 中封装成接口，支持 JSON 请求和 CSV 文件上传，并能返回结构化 JSON 或 Markdown 分析文本。

第四层是 AI 工作流。我把 FastAPI 服务部署到 Render 公网环境，然后在 Dify 中用 HTTP 请求节点调用这个 API，再由 LLM 节点根据 API 返回的 Markdown 自动生成门店经营分析周报、改进建议和典型差评回复。

这个项目不是简单调用大模型，而是先用 Python 做数据结构化，再通过 API 暴露能力，最后让 Dify 调用 API 完成报告生成，更接近真实 AI 应用落地流程。

## 三、3 分钟完整讲解版本

这个项目叫门店评论分析与自动回复 Agent，是我围绕门店经营场景做的一个 AI 应用项目。

项目背景是，咖啡店、餐饮店、本地生活门店每天都会收到很多用户评论，比如出餐慢、外卖撒漏、服务态度不好、环境卫生不及时、产品口味不稳定等。如果完全靠人工逐条看评论，不仅效率低，而且很难快速判断差评主要集中在哪些问题上。

所以我设计了一个流程：先用 Python 对评论数据进行结构化处理，再通过 API 把分析能力暴露出去，最后接入 Dify 工作流，由大模型生成门店经营分析周报和回复建议。

整个项目主要分为几个阶段。

第一阶段是本地 Python 数据分析。我准备了一份门店评论 CSV，字段包括 review_id、date、store_name、rating、content、category。Python 读取 CSV 后，会统计评论总数、平均评分、好评数量、中评数量、差评数量，以及好评 / 中评 / 差评占比。

第二阶段是差评筛选和问题分类。我把评分小于等于 2 分的评论定义为差评，然后通过关键词规则对评论进行分类。比如包含“等”“排队”“很久”的评论会归为等待时间；包含“外卖”“漏”“少送”的评论会归为配送物流；包含“服务员”“态度”“冷淡”的评论会归为服务态度；包含“桌面”“地面”“脏”的评论会归为环境卫生。这样可以快速统计差评主要集中在哪些问题上。

第三阶段是生成 AI 可用的结构化输入。Python 会把基础统计、分类统计、差评明细整理成 Markdown 文本。这样大模型不是直接面对一堆原始评论，而是面对已经整理好的统计结果和典型问题，输出会更有依据。

第四阶段是 API 工程化升级。原来的项目只能在本地运行 Python 脚本，我后面把核心分析逻辑从脚本中拆出来，放到 `review_service.py`，再用 FastAPI 在 `main.py` 中封装接口。目前接口支持三类能力：第一类是接收 JSON 评论数据并返回结构化分析结果；第二类是上传 CSV 文件并返回分析结果；第三类是生成 Coze / Dify 可用的 Markdown 文本。

第五阶段是公网部署。我把 FastAPI 服务部署到了 Render，生成了公网 API 地址。这样这个项目就不再只能在本地运行，而是可以被外部系统通过 HTTP 请求调用。

第六阶段是 Dify 工作流联动。我在 Dify 中搭建了一个工作流，用 HTTP 请求节点调用 Render 上的 FastAPI 接口，获取 API 返回的 Markdown 分析文本，再把这个结果交给 Dify 的 LLM 节点，自动生成门店经营分析周报。最终输出包括本周评论整体概况、差评主要问题、问题原因分析、优先改进建议、典型差评回复建议和下周运营重点。

这个项目里我也特别注意了 AI 输出边界。比如商家回复不能随便说“我们已经整改”“已经更换杯盖”“已经安排专人处理”，因为输入数据里没有这些事实。所以我在 Coze 和 Dify 的 Prompt 中都加入了边界规则，要求 AI 只能使用“会反馈”“后续会重点检查”“会尽快优化”这类克制表达，不能承诺退款、赔偿、免单，也不能虚构已经完成的整改动作。

这个项目目前还有一些局限，比如数据量比较小，分类主要基于关键词规则，复杂语义下可能误判；Dify 当前主要通过 JSON 请求调用 API，文件上传到 Dify 工作流还可以继续优化。但它已经完整跑通了“数据处理 → API 封装 → 公网部署 → Dify 调用 → LLM 报告生成”的流程。

通过这个项目，我主要学习到了 Python / Pandas 数据处理、FastAPI 接口封装、Render 公网部署、Dify HTTP 请求节点调用，以及如何把一个本地脚本升级成可以被 AI 工作流调用的应用服务。

## 四、项目架构说明

这个项目可以分成五层：

```text
数据层：门店评论 CSV / JSON
↓
处理层：Python / Pandas 统计、筛选、分类
↓
服务层：FastAPI 封装评论分析接口
↓
部署层：Render 公网部署 API
↓
应用层：Dify HTTP 请求节点 + LLM 节点生成经营周报
```

其中：
- Python 负责“算清楚”；
- FastAPI 负责“让外部系统能调用”；
- Render 负责“让 API 能在公网访问”；
- Dify 负责“编排流程并调用 API”；
- LLM 负责“把结构化数据生成经营分析报告”。

## 五、项目核心接口说明

项目中主要有几个接口：

```text

```

/analyze_reviews

```
/generate_coze_input
```

接收 JSON 评论数据，返回一段适合 Coze / Dify 使用的 Markdown 输入文本。

上传 CSV 文件，返回结构化 JSON 分析结果。

```text
/upload_reviews_csv_markdown_text
```

上传 CSV 文件，直接返回 Markdown 纯文本，方便复制到 Coze / Dify 进行分析。

## 六、我为什么要做 API 改造？

一开始这个项目只是一个本地脚本，只能通过：

```bash
python analyze_reviews.py
```

在本地运行。

这种方式能验证数据处理逻辑，但有几个问题：

1. 只能自己本地运行；
2. 外部系统不能直接调用；
3. 不能接入 Dify / Coze 这类工作流；
4. 不像真实业务系统。

所以我把分析逻辑封装成 FastAPI 接口。这样评论分析能力就变成了一个服务，外部系统只要发送 JSON 或上传 CSV，就可以调用我的分析功能。

这个改造让我理解了脚本和 API 的区别：

脚本是自己运行、自己看结果；
API 是别人通过请求调用你的能力，并拿到结构化返回结果。

## 七、Dify 工作流怎么接入？

Dify 工作流的结构是：

```text
用户输入
↓
HTTP 请求节点
↓
LLM 节点
↓
输出节点
```

HTTP 请求节点负责调用我部署在 Render 上的公网 API：

```text
https://store-review-analysis-agent.onrender.com/generate_coze_input
```

API 返回 Markdown 分析文本。

然后 LLM 节点读取 API 返回内容，根据 Prompt 生成门店经营分析周报。

最后输出节点展示最终报告。

这个流程实现了：

```text
Dify 调用 API
↓
API 返回结构化分析文本
↓
LLM 生成经营报告
```

相比之前手动复制 Markdown 到 Coze，这一步更自动化，也更接近真实 AI 工作流。

## 面试官可能追问的问题

### 1. 这个项目和直接让 ChatGPT 分析评论有什么区别？

直接让 ChatGPT 分析原始评论，可能会比较泛，而且缺少统计依据。

我这个项目先用 Python 做结构化处理，包括评分统计、差评筛选、分类统计和问题分布统计，再把结果交给 Coze 或 Dify 的 LLM 节点。这样大模型输出时会基于明确的数据，比如差评数量、差评占比、问题类别占比，而不是凭感觉总结。

所以这个项目的核心不是“让 AI 随便分析”，而是“先用代码整理数据，再让 AI 基于结构化结果生成报告”。

### 2. 你为什么不用大模型直接分类评论？

当前版本我先用了关键词规则分类，因为它简单、可控、容易解释，也方便我验证整个流程。

但它确实有局限，比如有些评论可能同时涉及多个问题，或者语义比较复杂，关键词规则不一定能准确判断。后续可以升级为规则分类 + 大模型语义分类，或者增加人工校正机制，提高分类准确率。

### 3. Python 在这个项目里主要做了什么？

Python 主要负责数据处理：

读取 CSV；
检查字段是否完整；
统计评论总数、平均评分、好评 / 中评 / 差评数量；
筛选评分小于等于 2 分的差评；
根据关键词规则给评论分类；
统计各类问题数量和占比；
生成 JSON 或 Markdown 格式的分析结果。

### 4. FastAPI 在这个项目里做了什么？

FastAPI 负责把 Python 的评论分析能力封装成 API。

也就是说，原来分析逻辑只能通过本地运行脚本触发，现在可以通过 HTTP 请求调用。

例如 Dify 可以请求我的 /generate_coze_input 接口，把评论数据发送过去，FastAPI 调用 Python 分析逻辑，然后返回 Markdown 分析文本。

### 5. Render 在这个项目里做了什么？

Render 负责把我的 FastAPI 服务部署到公网。

本地 API 地址是：

http://127.0.0.1:8000

这个地址只有我自己的电脑能访问。

部署到 Render 后，API 变成公网地址：

https://store-review-analysis-agent.onrender.com

这样 Dify 这类外部平台才能通过 HTTP 请求访问我的接口。

### 6. Dify 在这个项目里做了什么？

Dify 负责工作流编排。

我在 Dify 里搭建了：

```text
用户输入
↓
HTTP 请求节点
↓
LLM 节点
↓
输出节点
```

HTTP 请求节点调用我的 FastAPI 公网接口，LLM 节点读取 API 返回结果并生成门店经营分析周报。

所以 Dify 在这里不是替代 Python，而是负责把 API 和大模型串起来。

### 7. 你怎么控制商家回复不要乱承诺？

我在 Prompt 中加入了边界规则。

比如不能承诺一定退款、赔偿、免单，也不能说门店已经完成整改。因为用户提供的数据只是评论和统计结果，并没有提供真实处理结果。

所以回复里只能表达歉意、说明会反馈、会检查、会优化，不能虚构已经采取的措施。

### 8. 这个项目最大的不足是什么？

目前主要有几个不足：

第一，测试数据量比较小，只有 20 条模拟评论；

第二，评论分类主要基于关键词规则，复杂语义下可能不够准确；

第三，虽然 FastAPI 已支持 CSV 文件上传，但 Dify 当前测试主要通过 JSON 请求调用 API，Dify 直接上传 CSV 文件的流程还可以继续完善；

第四，当前还没有数据库，历史分析结果不能长期保存；

第五，还没有前端页面，普通用户无法直接通过网页上传文件查看报告。

### 9. 如果真实门店要用，还需要补什么？

如果真实门店要用，我认为需要补几个部分：

1. 接入真实评论数据来源，比如门店后台、美团、点评、外卖平台等；
2. 增加数据规模，支持按周、按月分析；
3. 优化分类方式，从关键词规则升级为 AI 语义分类；
4. 增加人工审核机制，尤其是商家回复不能直接自动发布；
5. 增加数据库，保存历史评论和分析报告；
6. 增加可视化图表，比如差评趋势、问题分布、评分变化；
7. 增加前端页面，让运营人员可以上传文件并下载报告。
